# Sliding-window Picard benchmark

Run on the local Intel Core Ultra 9 285K, using the Release build (`-O3`,
`OMPL_BUILD_VAMP=ON`, `OMPL_ENABLE_SDF_AVX2=OFF`). No AVX-512 is exposed by
this CPU. All configurations use the same executable and CBF implementation.

The six tracked UR5 `.problem` files contain 19 goals total. Their missing SDF
grids were regenerated from the current `ur5_nav` scene constructors using each
saved seed, 0.015 m voxels, and the exporter's default 0.30 m mount opening.
Existing starts and goal configurations were copied unchanged. `bake_grids.py`
records this regeneration; it ran in the existing `cbf-inc-rrt:local` container.

`run.py` runs four configurations serially and rotates their order across five
seed offsets (0, 100, 200, 300, 400): sequential CBF, Picard 8 nodes/1 worker,
Picard 8 nodes/4 workers, and Picard 16 nodes/4 workers. Picard gets at most two
iterations. Each process uses one trial per goal, a 2-second planner deadline,
the default adaptive certified-step cap, 0.05 s integration steps, kappa 19.8/s,
range 1.5 rad, zero additional self margin, the automatic interpolation buffer,
partial steering enabled, and the existing early-termination defaults.
Shortcutting is disabled. The included ordinary collision-checking baseline is
also executed by the demo, but is not the sequential-CBF comparator in this report.

Times are measured inside `planner->solve`: grid loading, setup, worker creation,
and final path auditing are excluded. Runs use matching sampler seeds, but the
steering methods can construct different search trees. These are end-to-end
planning measurements, not isolated filter-kernel timings. CPU affinity and
frequency were not pinned. Five seeds provide an initial comparison, not a
precise microbenchmark confidence interval.

`runs.csv` / `runs.json` record every CBF result; raw logs retain the other demo
output. A nonzero demo exit status of 3 means at least one goal was not solved,
not a runner crash. `summary.csv` is generated by `summarize.py`. Speed ratios
use only goal/seed pairs solved by all four methods, and are geometric means of
paired time ratios. Solve rates include every goal. Nonzero safety-audit counts
are retained independently of solve status; a planner-reported solve alone is
not evidence of a clean audit.

## Results

All configurations solved 80/95 goal-seed runs. All 10 wall-gap runs and the five
empty-scene high-reach runs timed out in every configuration. On the 80 common
solved pairs, median planner times were 0.416 ms (sequential), 1.572 ms (8/1),
3.094 ms (8/4), and 3.4145 ms (16/4). Paired geometric-mean slowdowns relative to
sequential were 3.93x, 7.20x, and 7.69x respectively. Median filter-call counts on
these pairs were 147.5, 607, 607, and 937 respectively.

The sequential shelf/lower_bay_right run with seed offset 0 reported seven
sampled states below the audited barrier margin. All Picard audit counts were
zero; all self-overlap counts were zero. These audits use the demo's sphere/SDF
model and sampling resolution, not a separate mesh-level continuous check.

The current threaded Picard implementation provides no speed benefit on this
suite. It increases filter work substantially, and four workers are generally
slower than one. SIMD batching was not implemented or measured.

## Adaptive windows and certified spans

A later run, after the window stopped being fixed and the committed segments
started spending their certificates. `adaptive_ab.py` runs three configurations
per scene and seed, rotating their order: sequential CBF, Picard 8/1 pinned to
the fixed `stepSize` grid (`picardAdaptive 0`), and Picard 8/1 adaptive
(`picardAdaptive 1`). Five scenes (`empty`, `pillars`, `clutter`, `shelf`,
`corridor`) and three seed offsets (0, 100, 200), three trials per goal, 2-second
deadline, otherwise the same settings as above. `wall_gap` is excluded: it timed
out in every configuration of the earlier run. `adaptive_ab.csv` records every
CBF result.

Both Picard configurations are the current implementation, so the pinned column
is not the code the section above measured -- it also carries the corrected
commit test and the relaxed map certification, which is why its own numbers moved.
What it isolates is the window rule and the spans, nothing else.

48 of 51 goal/seed pairs were solved by all three. Median planner time over those
pairs was 0.344 ms (sequential), 1.265 ms (Picard fixed) and 0.472 ms (Picard
adaptive); median filter calls 131.5, 565.5 and 171.5. Paired geometric means
against sequential: 4.09x slower on time and 4.54x on calls for the fixed grid,
1.39x and 1.30x for the adaptive one -- so the adaptive window and certified
spans together are 2.94x faster than the fixed grid at 3.49x fewer filter calls,
and close roughly three quarters of the gap to the sequential rollout.

Medians of planner time and filter calls over the pairs all three solved.

Safety audits are unchanged: one audited state below the margin, on
`shelf`/`lower_bay_right` at seed offset 100, in all three configurations
including sequential. No self-overlaps. Committed segments per window are now
close to one in clutter -- 989 map calls for 902 committed steps over 877 windows
on `corridor` seed 0, with the verification pass firing twice in the whole run --
so what is left of the gap is Picard's own bookkeeping rather than discarded
speculation. Widening the window again only pays once a window of `w` states
costs materially less than `w` filter calls, which is what SIMD across the window
would buy and threads demonstrably do not.
